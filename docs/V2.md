## 3. The design philosophy

1. **Answers before numbers.** A panel must say *how it is going* before it says what the
   number is. Score, trend and tone first; raw values second.
2. **Categories, not a queue.** Everything lives in a named part of life: Body, Mind, Attention,
   Capital. A panel with no category is a bug.
3. **One glance, zero clicks.** If understanding the home screen requires a click, a hover, or
   reading six numbers in a column, the design has failed. No expanders on the dashboard.
4. **The chart is the sentence.** Where a shape carries the meaning better than a figure —
   sleep, steps, the score over time — draw it. Never decorate with a chart that says the
   same thing as the number next to it: a row you log in one tap shows its cells, and a signed
   trend shows its figure.
5. **Logging is a gesture, not a form.** One tap sets a value. No save button, no modal, no
   submit — the write is optimistic and undoable with ⌘Z.
6. **Quiet, not empty.** Hairline rules, one accent, generous space. Beauty comes from
   proportion and restraint, not decoration.
7. **Fast is a feature.** ≤ 90 KB gzipped, no chart library, no CDN font, no runtime dependency.
   Every visual is hand-drawn SVG.

### Type
One self-hosted variable family (Inter) for text, monospace tabular figures for anything
numeric — this is what makes the screen read like an instrument rather than a form.
Colors, sizes, spacing and motion stay in `src/styles/tokens.css`. **No hardcoded values.**

Open option, only if the dashboard feels flat once it is built: subset a single display face
to ≤ 15 KB for the hero readout, staying inside the 60 KB font budget. Do not add a second
full family.

### Palette of charts
All hand-written SVG, all tokenised, all keyboard- and screen-reader-labelled:
area/line (score over time, weight, sleep duration), bars (steps, hours, deep blocks),
dots/heat (consistency, habit coverage), ring (the day's score), and the existing heat grid.
Pick per metric by `widget` + cadence, defined in one place.

## 4. What we focus on now — in this order

1. **Design.** The dashboard is the product. If it is not beautiful and legible, nothing else
   matters.
2. **Data display.** Categories, charts, hierarchy, tone. Can it be read at arm's length?
3. **Logging ease.** Log from the dashboard in one tap. `/log` remains the full logger.
4. **Data automation.** Apple Health in, without accounts and without a third party.

Everything else — new metrics, new screens, sync, PWA — waits. `docs/spec/08-build-plan.md`
M6–M9 stay unplanned.

### Definition of done for V2
- The home screen tells you what is going on **without a single interaction**.
- Every panel is categorised and has one chart where the shape matters.
- A value can be logged from the dashboard without leaving it.
- Correct and beautiful at 320 px, 390 px and 1440 px, light and dark.
- `npm run check && npm test && npm run lint && npm run build && npm run e2e` clean.

## 5. Data automation — Apple Watch

**Constraint:** a web page cannot read HealthKit. The app is static and local-first, so there is
no account, no cloud and no third party in the middle. The honest pipeline is:

```
 Apple Watch ──▶ iPhone Health ──▶ Health Auto Export / Shortcut ──▶ POST
                                                                      │
                          ┌───────────────────────────────────────────┘
                          ▼
      self-hosted server:  POST /ingest/health  (token, same machine)
                          ▼
      data/health.json  ──▶  GET /data/health.json
                          ▼
      the site merges it by date on load; a missing day stays a gap
```

- **Server side** (`server/serve.py`): accept `POST /ingest/health` with a generated token,
  validate the shape, merge into `data/health.json`. Reject anything else. The token and the
  exact URL are shown on the site so it can be pasted into the phone app.
- **Client side**: fetch `/data/health.json` once per session, merge by date into the auto
  metrics (`sleep_hours`, `sleep_consistency`, `steps`, `weight_trend`, `daylight_days`). A
  fetched value is never invented: a day with no row stays unset.
- **Fallback, always:** every auto metric is already hand-enterable from its own cell, so the
  dashboard is never wrong about a day the automation did not cover.
- **On the site**: a "Connect" panel (from Settings and from the dashboard when nothing has
  arrived yet) showing the ingest URL, the token, the last received timestamp, and the recipe.

Not built and not planned: OAuth, any hosted service, any account. If it needs a login, it is
out.


Every row is one metric of that pillar: a label with its unit, then the value, then either a
chart or the cells you log it with. The control *is* the readout, so a hand-logged row never
prints the same figure twice.

Rules the layout obeys, and where they live in the code:

- **Every panel** carries a `SectionLabel`, a pillar score, a 30-day sparkline and a line
  saying how many of the window's days were scored. `panelFor()` in `src/lib/dashboard.ts`.
- **Charts per metric** are chosen by widget + cadence, never by hand per metric:
  `chartFor()` returns bars for a numeric daily or weekly metric; nothing for a row you log in
  one tap (the cells are the readout), for a monthly figure (too few points to be a shape) or
  for a signed trend (a bar chart from a zero baseline cannot draw it). Both charts are
  hand-written SVG — `src/lib/ui/Bars.svelte` (14 days, or 6 weeks, with the target as a
  hairline) and `src/lib/ui/AreaChart.svelte` (the hero, fixed 0–100). The bar chart scales to
  the window but stops at the value that scores nothing (`stretch`, or `bad` for a `range`), so
  one wild day cannot flatten the other thirteen.
- **A gap stays a gap.** Every series is `(number | null)[]`; a missing day draws no bar and
  breaks the area rather than interpolating across it.
- **Inline logging** uses the existing cell components (`TriState`, `ChoiceRow`, `Segmented`,
  `Bins`, `NumberField`) — tested, keyboard-complete, already at the 44 px floor. `inlineControl()`
  offers them for a *daily* cell metric and for the *monthly* figures; a weekly counter gets
  none, because it logs into a day and would read as "sessions today" under a label that says
  `/wk`. `NumberField` is how a monthly number is entered: the dashboard is the only screen that
  shows `savings_rate` and `invested` at all. Writing goes through the same `writeValue()` as
  `/log`, so there is one code path and one undo.
- **No expander, no form, no save button.** A tap writes immediately.
- The panels are ordered **by what needs attention first**, read on the 28-day figure and
  compared rounded so the order matches the figures on the screen, ties broken by the registry
  order. The page freezes that order for the visit (D18), so nothing moves while you log.
- **The measure widens.** `.shell` stays 620 px everywhere; the dashboard and the top bar above
  it use `--measure-wide: 1040px`, two panels per row above 840 px, one below.

## 7. Carry-overs from v1 that are still binding

- Local-first. No accounts, no analytics, no third-party request at runtime.
- Tokens only: no hardcoded colour, size or font (`src/styles/tokens.css`).
- No new runtime dependency. Banned: chart libraries, UI kits, state managers, date
  libraries, CSS frameworks, icon packs, CDN fonts.
- Keyboard-complete. 44 px targets. Reduced motion honoured. AA contrast.
- Pure logic is unit-tested; user-visible behaviour is covered by Playwright.
- Never invent a metric, target or weight: `docs/spec/02-metrics.md` is still canonical for
  those values, and `docs/spec/03-scoring.md` for the maths.
